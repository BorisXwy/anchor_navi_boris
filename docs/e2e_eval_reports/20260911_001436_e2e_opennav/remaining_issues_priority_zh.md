# OpenNav100 全量轮之后：剩余硬性问题按优先级排序（2026-09-11）

- 依据：`docs/e2e_eval_reports/20260911_001436_e2e_opennav/report_zh.md`（100 条全量轮的详细分析）以及 `scripts/` 源码静态阅读。
- 前提：崩溃问题（`rgb_only_instruction_sequence.py` 未捕获的选点 `RuntimeError`）已于 2026-09-11 修复（commit `272c223`），本文只列**修完之后**仍然存在的问题。
- 排序标准：修好以后能多救回多少局 × 修法有多确定。
- 状态说明：除第 1 位的根因（已在产物与源码中确认）外，各项的"怎么修"都是**建议**，尚未实施、尚未验证。

## 系统一句话

系统像一个拿着地图碎片找路的人：先把长指令拆成几句（"右转"→"沿红地毯走"→"穿过门"→"在玻璃板旁等"），每一句都做三件事——**看一圈选个落脚点**（选点）→ **走过去**（走路）→ **问一个裁判"这句算完成了吗"**（判定）。裁判说"完成"就做下一句；说"不确定"就把这个方向封掉、退回去换方向再试；同一地点封满 5 个方向就放弃整局。最后一句判"完成"后主动喊 STOP，STOP 落点离终点 3 m 内才算赢。

## 第 1 位：转弯动作根本没被记下来，裁判永远看不见你转过弯

**现象**：100 条指令里有 104 句是"左转/右转/转身"（TURN_LEFT 51、TURN_RIGHT 45、TURN_AROUND 8），几乎每条指令都有一句。裁判对这类句子的判决是 **13 次"完成" vs 90 次"不确定"**，90 次里 **78 次的理由原话是"动作记录里只有前进、0 次转向命令"**。

**真实原因**（源码已确认）：系统选好落脚点后会先原地转到那个方向，这一段转身动作由 `point_selectors.continuous_turn()`（`point_selectors.py:808`）执行，记在 `motion_log` 上；而交给裁判看的 `action_history` 由 `PointNavigationExecutor.execute()`（`point_navigation_executor.py:1020-1022`）从空列表开始记，只含走路阶段。边的 `action_history` 和 `edge_keyframes` 都来自执行器，所以裁判看到的永远是"一直往前走"。样本：id 469 第一跳 `selected_action_heading_rad=-90°`、方向门 `right`、`allowed_views=[5,6,7]`，实际已右转 90°，`action_history` 却是 12 条 `move_forward`，裁判理由"12 次前进、0 次右转命令"→ 不确定。

**连锁反应**：第一句就是"右转"→ 裁判说不确定 → 封方向 → 退回 → 再试 → 再不确定……75 条崩溃里 **38 条**卡在转弯句上（TURN_LEFT 18、TURN_RIGHT 13、TURN_AROUND 6、TURN_TO_LANDMARK 1），31 条在第一句话就死了。

**怎么修**：把 `continuous_turn` 产生的 `turn_left`/`turn_right` 并进该边交给裁判的 `action_history`，关键帧的起始帧取转身前那张。不改任何导航决策，只让裁判看到真实发生的事。按规则先在 id 469 / 546 的真实状态上单点复现（预期：判定理由不再出现"0 次转向命令"），再十 EP 回归。

**预期**：唯一一个"原因确定、修法机械、覆盖面几乎 100%"的问题。

**已于 2026-09-11 修复**（`rgb_only_instruction_sequence.py`：每跳从 `motion_log` 取出 `turn_to_selected_target` 阶段实际发出的 `turn_left/turn_right`，作为 `step -T..-1`、`orientation_only=True`、`phase="turn_to_selected_target"` 的 RGB-only 动作记录前置到该边 `action_history`，并把转向前的前视帧存为 `edge_keyframes/target_XX_turn_start.jpg` 作第 0 张关键帧；八视图 refinement probe 不计入；执行器、选点器、判定 prompt 均未改）。新增测试 `tests/test_rgb_only_instruction_sequence.py::RGBOnlySequenceTurnHistoryTests`、`tests/test_rgb_only_edge_judge.py::test_turn_to_view_actions_are_counted_and_kept_in_prompt`，全量 314 个单元测试通过。
真实 state 单点复现 `outputs/e2e_eval/20260911_113312_turn_history_smoke`（id 469、546，单 worker，2 条 `returncode=0`、契约审计通过）：两条的第一跳 "Turn right" 都在**第一次判定即 completed**（469 理由原话 "6 right-turn commands totaling ~90°"；上一轮分别耗了 3 跳、5 跳且各封锁 1 个方向）；裁判 prompt 里 `right_turn_command_count=6`。469 仍在 17.4 m 处误 STOP、546 终点 3.44 m（上一轮 5.09 m）——这是第 3 位（判定假阳性 / 保守）的问题，本项只保证裁判看到真实转向。未做十 EP 回归、未冻结。后续项：`RGBOnlyGraphBacktracker.recover()` 的 `rgb_only_backtrack_turn` 仍只记在 `motion_log`（回溯边不经裁判，影响较小）。

## 第 2 位：转弯句的"方向门"一空就整局结束

**现象**：说"右转"时，选点器只允许看右边 2–3 个摄像头（方向门 `direction_gate`）。这几个画面里没有可走地面、或被封了一两个方向，候选就空了（`vlm_harness.py:2929` "No floor-bearing candidate remains inside the explicit right/left/rear direction gate"）——**24 条**因此终止（右 9、左 9、后 6），其中 **6 条一步都没走**（id 52、150、207、643、765、1087：第一句就是转弯或出房间，那一侧恰好没地面）。修完崩溃后这些变成优雅结束，但仍是整局零进展。

**为什么不合理**："右转"本质是个**旋转**指令，不是"往右边某块地走"。右边没地面时更合理的做法是原地转到位后重新看一圈，而不是宣布全局失败。

**怎么修**：给方向门加一个按指令形式（TURN_*）定义的兜底：门内无候选 → 原地按指令方向转到位 → 重新选点（或至少放宽到相邻 45° 视图）。这是按"指令形式"抽象的规则，不是针对某个 episode 的补丁，符合 `project_rulle.md` 16.4。

**预期**：直接救回 24 + 6 条的"开局"；与第 1 位叠加——裁判能看到转弯后，封方向次数减少，门也不那么容易被清空。

## 第 3 位：裁判太保守，偶尔还乱点头

**现象**：
- 全部 498 次判决里 **395 次（79%）是"不确定"**；排除转弯句，其它句子也有 77% 不确定。置信度基本是两个固定值（完成约 0.7、不确定约 0.6），没有信息量。
- 正常结束的 25 条里 17 条是"同一地点封满 5 个方向"放弃的，其中 **11 条一句都没完成**，平均起点 9.65 m → 终点 9.59 m，零进展；8 条终点比起点还远。
- **11 条崩在最后一句"在某处等"（STOP_WAIT）**上（id 187、259、321、411、479、513、586、1106、1142、1301、1307）——人已到终点附近，裁判不肯说"完成"，STOP 发不出去。
- 反向错误：8 次 STOP 里 **2 次乱点头**——id 469 四句全判"完成"，终点离目标 16.3 m、比起点还远；id 546 在错误房间 STOP。

**怎么修**：先别改 prompt。先对本轮跑独立复核脚本 `verify_round_stage_completions.py`（花一点 VLM 费用），搞清楚 103 个"完成"里多少是真的、395 个"不确定"里多少其实已经到了。有了这张表才知道是 prompt 太苛刻、到达点确实不对、还是裁判看的画面不够。

**预期**：成功率的真正天花板——选点和走路都对，裁判不点头也不能推进。但它没有明确 bug，属于数据驱动调优。

## 第 4 位：走路层说"到了"的时候，其实还差一点

**现象**：走路层 155 次报"到达"，隐藏几何显示中位数离目标点 **0.94 m**，90% 在 1.5 m 内，但按项目 0.75 m 的严格口径只有 **48 次（31%）算真到**（`arrival_signal_precision=0.30`、`recall=0.92`）。另外 34 次"走满 20 步没到"里有 5 次其实只差 1.2 m 以内；批量入口 `evaluate_point_navigation.py` 默认 `--max-steps-per-target 20`，单条入口 `habitat_point_navigation.py` 默认 32，两处不一致。

**影响**：站在差 1 m 的地方让裁判判"到没到"，裁判更容易说不确定（回到第 3 位）；最后一句 STOP 也会偏。

**怎么修**：先把 20 对齐到 32（配置对齐，但规则要求当独立候选做十 EP 回归）；再看 GNM 密集停止簇的到达阈值。

## 第 5 位：长指令、远距离基本没戏（结构性）

**现象**：6 条成功（id 11、308、531、670、698、810）起点距目标都在 5–9 m、2–5 句；**没有一条起点 >10 m 的成功**；7–8 句的指令全部失败。

**原因**：每一句通过率约两三成，五句连乘接近零。不是单独 bug，而是 1–4 的累积；前三位修好会自然改善，单独针对它做任何事都是徒劳。

## 第 6 位：零碎但值得顺手处理

- `scripts/audit_active_stop_round.py` 只认固定十 EP 索引，对 `run_e2e_eval.sh` 的分片目录会找到 0 条并**覆盖轮次根目录的 `summary.json`**（`:556`），而 `run_end_to_end_eval.py` 结束提示里仍列着它——应从提示里去掉或改成写独立文件。（恢复办法：用 `run_end_to_end_eval.merge_shards()` 从 `shard_N/summary.json` 重新生成。）
- id 116：DeepSeek 连续 3 次返回缺 `view_index` 字段的 JSON（1%），且 `vlm_calls_attempts.json` 失败尝试没保存原始响应，无法进一步排查——建议失败尝试也留 raw response。
- 种子固定但云端 VLM 输出不确定（id 11 两轮跳数不同：2 跳 / 0.73 m vs 3 跳 / 0.81 m），十 EP "冻结"口径需有心理准备。

## 建议执行顺序

1. 第 1 位 + 第 2 位（同属"让系统如实表达自己做了什么 / 把转弯当转弯处理"），在 id 469、546、52 的真实状态上单点验证，再十 EP 回归。
2. 同时对本轮跑一次 `verify_round_stage_completions.py`，拿到第 3 位的数据。
3. 第 4 位的配置对齐作为独立候选回归。
4. 以上完成后再考虑下一次全量（预计 2–2.5 小时、约 1200 万 token、约 3 GB 磁盘）。

禁止事项（`project_rulle.md` 16.4）：不得按 episode / 场景 / 物体名 / 固定像素写条件分支；上述修法均须抽象为指令形式、动作历史或时序规则，并在未参与调参的真实状态上回归。
